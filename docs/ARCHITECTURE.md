# Архитектура системы «Инспектор ИИ — Стройнадзор Москвы»

## 1. Концепция и системный дизайн

Система «Инспектор ИИ» построена по принципу модульной слабосвязанной архитектуры с обеспечением строгой детерминированности, юридической значимости результатов и полной трассируемости решений.

### Ключевые архитектурные принципы:
1. **Explainable AI (Объяснимый ИИ):** Ни один вердикт системы не принимается как «черный ящик». Каждое выявленное несоответствие обязательно снабжается точной ссылкой на первоисточник: нормативный пункт (СП/ГОСТ), номер листа, шифр чертежа, ревизию и визуальный Bounding Box.
2. **Human-in-the-Loop (Человек принимает решение):** Нейросетевые алгоритмы выполняют роль модуля предварительной автоматической верификации, формируя кандидатов на нарушения. Окончательный юридический статус фиксируется государственным строительным инспектором.
3. **Неизменяемость аудита (WORM Architecture):** Каждое действие инспектора, супервайзера и алгоритма логируется в формате Write Once, Read Many с вычислением криптографического хеша.
4. **Стандартизация по ПП РФ № 87 и ГОСТ Р 21.101-2020:** Все внутренние сущности нормализованы по разделам проектной документации и реквизитам основной надписи.

## 3. Модель данных и сущности

### 3.1. Объект строительства (`ConstructionObject`)
```typescript
interface ConstructionObject {
  id: string;
  name: string;
  address: string;
  customer: string;
  contractor: string;
  permit_number: string;
  status: 'GREEN' | 'YELLOW' | 'RED';
  active_protocol_id: string;
  created_at: string;
  scenarios: {
    upload_scenario: UploadScenario;
    stage_statuses: {
      pd: StageUploadStatus;
      rd: StageUploadStatus;
      id: StageUploadStatus;
    };
  };
  stats: ObjectStats;
  iais_rin_sync: IaisRinSyncInfo;
}
```

### 3.2. Матрица контроля 132 параметров (`ControlParam`)
Каждый параметр строго типизирован и содержит:
- **Раздел ПП РФ № 87** (`ПЗ`, `СПЗУ`, `АР`, `КР`, `ИОС1-5`, `ПОС`, `ППМ`, `ОДИ` и др.);
- **Правило сопоставления (`trigger_logic`):** Алгебраическое выражение или логическое правило (например, `RD.beam_cross_section < PD.beam_cross_section`, `ID.concrete_grade != RD.concrete_grade`);
- **Нормативная ссылка:** Пункт СП, ГОСТ или ФЗ;
- **Допустимые отклонения (Tolerances):** Числовые пределы погрешности строительно-монтажных работ согласно нормам.

### 3.3. Результат проверки параметра (`CheckFinding`)
- **Статусы (`FindingStatus`):**
  - `NEGATIVE_VERIFIED` — Проверено, замечаний нет (полное соответствие нормам и ПД);
  - `CANDIDATE` — Автоматически обнаруженное отклонение, ожидающее решения инспектора;
  - `CONFIRMED_VIOLATION` — Нарушение подтверждено инспектором (включается в Предписание);
  - `MISSING_EVIDENCE` — Отсутствует обязательный подтверждающий документ (например, нет акта АОСР);
  - `NOT_APPLICABLE` — Параметр не применим к типу объекта;
  - `NOT_COMPARABLE` — Невозможно сопоставить из-за отсутствия исходных слоев/осей;
  - `CLARIFICATION_REQUIRED` — Запрошены дополнительные пояснения у ГИПа/проектировщика;
  - `SUSPICION` — Косвенный признак фальсификации или системной ошибки.

## 5. Модель безопасности и неизменяемый аудит (WORM)

1. **Ролевой доступ:** Разделение привилегий между инспектором, супервайзером, аналитиком и администратором.
2. **WORM-логгирование:** Записи журнала аудита не подлежат редактированию или удалению.
3. **Хеш-цепочка:** Каждое событие содержит:
   - Временную метку ISO 8601;
   - Идентификатор пользователя и его сертификат УКЭП;
   - Идентификатор объекта и протокола проверки;
   - Код выполненного действия;
   - Криптографический контрольный хеш (`worm_hash`), исключающий подмену истории проверок.
